# 0005. Межі модулів перевіряються автоматично (dependency-cruiser)

## Контекст і постановка проблеми

Модульний моноліт (ADR-0001) тримається лише на тому, що модулі не лізуть у внутрішні файли
один одного, залежності йдуть в одному напрямку, а SQL і фреймворки не розповзаються по коду.
У моноліті межу можна порушити одним імпортом, і код-рев'ю цього надійно не помічає. Як зробити
межі з spec §3 перевірюваними так, щоб порушення блокувало коміт?

## Чинники рішення

- Порушення виявляється до коміту (pre-commit) і в CI, а не на рев'ю.
- Правила виражають саме нашу архітектуру: шари, публічний API модуля, напрям потоку даних,
  де дозволені SQL-драйвер, черга, HTTP-фреймворк, логер.
- Враховуються type-only імпорти (контракти між модулями — переважно типи).
- Правило має назву й пояснення, яке можна звірити зі spec.

## Розглянуті варіанти

- dependency-cruiser з власним набором правил
- ESLint `import/no-restricted-paths` / `no-restricted-imports`
- TypeScript project references (окремий `tsconfig` на модуль)
- Лише код-рев'ю

## Рішення

Обраний варіант: «dependency-cruiser з власним набором правил», тому що він виражає всі наші
типи меж (шари, публічний API через `$1`-групи, напрям між модулями, обмеження npm-пакетів,
цикли, сироти) в одному декларативному файлі і перевіряє весь граф, включно з type-only імпортами.

### Наслідки

- Добре, тому що межі описані один раз у [`.dependency-cruiser.cjs`](../.dependency-cruiser.cjs),
  кожне правило має `comment` і рядок у spec §3.4 (синхронність перевіряє `docs:check`).
- Добре, тому що порушення блокує коміт (pre-commit) і merge (CI).
- Добре, тому що `npm run deps:graph` генерує актуальну діаграму залежностей для аудиту.
- Погано, тому що ще один інструмент і конфіг на ~200 рядків, який треба підтримувати.
- Погано, тому що регулярні вирази шляхів крихкі: перейменування теки без оновлення правил тихо
  вимикає правило. Пом'якшення — навмисні порушення перевіряються при зміні конфігурації
  (див. defense/lab1), а `no-orphans` ловить файли поза очікуваною структурою.

### Підтвердження

- `npm run deps:check` у pre-commit, pre-push і CI.
- При зміні правил: тимчасові файли-порушники мають бути виявлені (процедура й результат —
  у [defense/lab1/DEFENSE.md](../defense/lab1/DEFENSE.md)).

## Переваги та недоліки варіантів

### dependency-cruiser

- Добре, тому що правила від/до з групами захоплення (`^src/modules/([^/]+)/` → `pathNot $1`).
- Добре, тому що розрізняє типи залежностей (npm, npm-dev, type-only, core) — звідси правила
  `no-dev-deps-in-runtime`, `domain-is-pure`.
- Погано, тому що окремий від ESLint звіт.

### ESLint import/no-restricted-paths

- Добре, тому що вже є ESLint, помилки видно в редакторі.
- Погано, тому що немає виявлення циклів на рівні модулів без `import/no-cycle` (повільний на
  великому графі), немає сиріт і типів залежностей; правила «будь-який модуль → лише `index.ts`
  іншого модуля» виражаються переліком усіх пар.

### TypeScript project references

- Добре, тому що межа на рівні компілятора.
- Погано, тому що окремий `tsconfig` на кожен модуль, складна збірка; не виражає «SQL лише в
  репозиторіях» чи «pino лише в platform».

### Лише код-рев'ю

- Добре, тому що безкоштовно.
- Погано, тому що люди пропускають імпорти в diff; одна людина в проєкті — рев'ю немає кому робити.

## Додаткова інформація

Переглянути, якщо модулі буде винесено в окремі пакети workspace — тоді межі частково перейдуть
у `package.json` кожного пакета.
